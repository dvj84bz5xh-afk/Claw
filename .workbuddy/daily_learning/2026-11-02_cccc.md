## 学习日期: 2026-11-02

### 学习项目: ChesterRa/cccc
- URL: https://github.com/ChesterRa/cccc
- Stars: 1,292 (Rust, Apache-2.0, v0.4.46, 更新 2026-10-30)
- 定位: **协作内核（collaboration kernel）** —— 不是编排器、不是 Agent 框架，而是让多个**不同厂商的 Agent CLI** 像群聊一样协作，并把"消息是否真的送达/被读/被回"变成可查的事实
- 与现有场景直接对应: IM 桥支持 Telegram/Slack/Discord/Mattermost/**飞书**/钉钉/企微/微信

### 核心发现

**1. 协作状态归 daemon 单写者，历史是 append-only ledger**
`ledger.jsonl` 只增不改；Group 配置与共享 context 各有独立权威存储；运行时状态在 `CCCC_HOME`（默认 `~/.cccc/`）**与仓库物理分离**。Web UI / CLI / MCP / IM 四个端口**共用同一个 control plane**，不存在"从某个端口改的状态另一个端口看不见"。

**2. 一条消息拆成四个独立事实，互不冒充**
`stored`（已落账）/ `runtime.delivery`（进程真的收到了）/ `read`（读游标）/ `reply`（答复）/ `cancellation` / `task completion` —— 每一个都是独立记录。
这是本轮最有价值的一条：Claw 现在只有"消息已发"一个状态，于是"我以为它知道了"和"它确实知道了"无法区分。

**3. 三种显式投递模式，配套一条使用规则**
- `Send` —— 主动打断式投递
- `Send + Reply` —— 要求一个具体答复，**跟踪到对方回复或发送方取消为止**
- `Mail` —— 不打断，进 Inbox，**按 ledger 顺序消费**，`cccc_inbox_read` 返回下一批并**原子推进** Mail 游标

规则写得很克制："能等的用 Mail；延迟知晓的代价大于打断，才用 Send；只有还需要一个具体答案时才 Send + Reply。`@all` 只用于公告或紧急协调，不该是开始具体工作的默认方式。Mail 不能发给人类用户。一条消息要么只面向 user，要么只面向一个/多个 agent —— 不要混着发。"

**4. `tracked-send` = 委派单据，不是一条消息**
当委派工作需要 **durable owner / outcome / evidence / handoff / acceptance trail** 时用它。CLI 里就是 `--title` + `--outcome` 两个必填语义。
→ Claw 的 `TaskCreate` 现在是"待办条目"，缺的正是 outcome 与验收证据：一个任务可以被标 completed，却没有任何东西证明它被满足。

**5. 角色与生命周期边界**
Foreman + peer 模型，权限边界 + 路由（`@all` / `@peers` / `@foreman` / 指定 actor id）。更关键的是：**paused / stopped / disabled 的 actor 不会被投递静默唤醒** —— 消息不会"投给一个已停机的 agent，然后发送方以为它收到了"。

**6. 运维是策略，不是提示词**
内置五条：Mail notice（**最多一次、无内容**提醒）、Reply notice、Actor 空闲检测（通知 foreman）、Keepalive、Silence 检测（整组静默告警）。自定义规则支持 interval / cron / one-time，动作可改组状态、控 actor 生命周期（**admin-only 且只能 one-time**，防止定时规则变成绕权通道）。

**7. MCP 工具面分级：常驻"协作协议"核心，其余按需**
常驻只有 `cccc_bootstrap` / `cccc_help` / capability search+use / inbox / messaging / files / `cccc_context_get` / `cccc_coordination` / `cccc_task` / `cccc_agent_state`；`tracked_send`、`memory`、`context_sync`、`group`、`actor`、`runtime_list`、`repo`、`presentation`、`terminal` 全走 `cccc_capability_use` 按需调用。
分级维度不是"重要/不重要"，而是**"协作协议本身" vs "可选机械"** —— 协议常驻保证任何 session 都能协作，机械按需保证不污染上下文。

**8. 多运行时 + 已存在会话可加入**
每个 actor 可用不同 runtime（Claude Code / Codex / Cline / Copilot / Cursor / Devin / Kiro / Kilo / Antigravity / ChatGPT Web / Dots / Grok Bot / custom）。0.4.46 起**用户自己已经开着的 Codex / Claude Code / Pi / OpenCode 会话可以直接加入 Group**，各自保留自己的进程、会话、账号与审批，**不导入历史**。

**9. 跨实例授权粒度极细**
同账号自动发现 / 不同成员需双方各自确认 Group 对 / Direct 免账号但需可信通道交换邀请。跨成员只授予**消息、回复、小文件** —— 不授予终端、工作区浏览或任意工具；远程工作台必须用**目标实例自己的 admin token**。

**10. 安全边界写得诚实，且与 nono 形成对照**
"Web UI 是高权限面，非本地暴露前先建 Admin Access Token；**daemon IPC 是可信本地接口、没有应用层认证**；**capability allowlist 不是原生 agent 进程的沙箱**，请自行审查 runtime 的权限与自主度默认值。"
—— 它明确承认自己**不是安全边界**。这与 10-29 nono 正好互补：nono 管"进程能碰什么"，CCCC 管"谁该知道什么"，两者都拒绝越界承诺。

### 改进建议
1. **P0 · agent_orchestrator — 协作消息四态化**
   现在子 Agent / 团队成员之间只有"消息已发"。改为记录四个独立事实：`stored`(落账) / `delivered`(对端进程确认收到) / `read`(读游标) / `replied`(答复)，任一不可由另一推断。价值：把"我以为它知道了"这类协作失败从**事故**变成**可查字段**；这也是让 Team（WorkBuddy+Claude Code+Hermes）从"人工在飞书群里转述"升级为可自动化的前提。

2. **P0 · agent_orchestrator — 三模式投递 + Mail 原子游标**
   `send`（打断）/ `send_and_reply`（跟踪到回复或取消）/ `mail`（不打断，按序消费，读游标原子推进）。默认用 mail；只有延迟成本 > 打断成本才 send；`@all` 只用于公告。价值：减少"每条协作消息都是一次全上下文唤醒"的成本，且让恢复语义明确（游标不丢、不重复）。

3. **P0 · claw_integration — 委派单据（tracked-send）**
   TaskCreate 升级为带 `owner` / `outcome`（完成的可观测定义）/ `evidence`（证据链接）/ `handoff`（接手人）/ `acceptance`（签收人）的委派单；未填 outcome 的任务不得进入 in_progress，未附 evidence 不得标 completed。价值：直接补上"改进项只计数不验证"的另一半 —— 让每条任务自带验收口径。

4. **P1 · agent_orchestrator — 生命周期边界**
   paused / stopped / disabled 的 agent 不得被投递唤醒，投递方必须收到"未投递：目标已停用"的明确失败，而不是静默排队。价值：防止"发给一个死掉的 agent 然后以为它在干活"。

5. **P1 · eval_observability — 运维策略事件化**
   idle 检测、整组静默、notice（**最多一次、无内容**）作为事件而非提示词注入；自定义规则限 interval/cron/one-time，改变组状态与生命周期的动作限 admin 且只能 one-time。价值：告警不占上下文，且定时规则不能变成绕权通道。

6. **P2 · tool_registry — 工具面按"协议 vs 机械"分级**
   常驻只留协作协议所需的最小集合，其余（记忆、同步、仓库、终端、演示）走 `capability_use` 按需调用。

### 判断
Claw 的 swarm 是**进程内**并行，Team 协作是**人类在飞书群里手动转述**。两者之间缺一层：跨进程、跨 runtime、带投递事实与委派单据的协作层。CCCC 恰好就是这一层，而且它明确不做编排（"纯 DAG 编排 → 用专用 orchestrator，CCCC 可互补"），边界干净。

但**不建议直接引入** CCCC 作为依赖：它是 Rust daemon + Web UI + 账号体系，比 Claw 现有规模重得多。真正该抄的是三个语义：
1. **消息四态**（送达 ≠ 已读 ≠ 已回）
2. **委派单据**（owner + outcome + evidence + acceptance）
3. **生命周期边界**（停用的 agent 不被投递唤醒）

这三条加起来只改数据结构，不改架构 —— 而它们解决的正是"多 Agent 协作时，谁也不知道对方到底走到哪一步"这个每天都遇到的问题。
