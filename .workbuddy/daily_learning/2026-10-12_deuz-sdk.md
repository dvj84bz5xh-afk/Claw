## 核心发现
1. **Durable Execution = Lease(存活) + Revision(围栏) 双机制** — Lease 决定"此刻哪个进程驱动这个 run"，心跳续租；Revision 是围栏，每次提交都声明期望版本号，store 拒绝陈旧版本 —— 即使"僵尸执行器"醒来也无法覆盖接管者的进度。支持跨进程 cancel(针对 run，跨持有人保留) / drain(针对当前持有人，随 lease 丢弃) / 恢复
2. **持久化预算 BudgetStore（reserve-then-settle）** — 按 user/thread/org 维度的 token + USD 预算，跨所有 run 和所有进程共享；准入时先**预留估算值**，调用后**结算实际用量**，第二个 run 在任何模型调用前就直接失败；支持滚动窗口 + 告警
3. **Guardrails = 4 个普通函数钩子 × 3 种判决** — `onInput`/`onToolCall`/`onToolResult`/`onOutput`，每个返回 pass/block/rewrite；纯函数、无时钟/无随机/无 I/O，edge-safe；所有非 pass 判决按序记录进 `providerMetadata.deuz.guardrails` 供审计；并明确划分"该用 guardrail（针对本次 run 的策略）" vs "该用 request validation（请求体校验，在循环前拒绝而非修复）"
4. **Evolve — 进化式程序搜索（AlphaEvolve 风格）** — `EVOLVE-BLOCK-START/END` 标记可进化区段；模型产出 SEARCH/REPLACE diff；**评估级联(evaluation cascade)** 打分；islands 分区 + **模型 bandit** 分配算力；**强制预算**（必须声明）；**zero-call resume**（断点恢复不重复调用模型）
5. **Swarm = 固定 DAG + 事务化持久化** — 调度器**先持久化 task dispatch 再开始工作**，结果与控制事件**原子提交**；无事件订阅者也能继续执行；bounded concurrency；`definitionVersion` + 每个 agent 的 `version` 可追踪
6. **零依赖 + 可选 peer 设计** — core 零必需运行时依赖，集成走 optional peers；未引用 built-in 就不会被打进 bundle

## 可借鉴点
| 优点 | 优先级 |
|------|--------|
| Durable execution: Lease(存活)+Revision(围栏) 双机制, 跨进程接管/取消/drain/恢复 | P0 |
| 持久化预算 BudgetStore: reserve-then-settle 准入, 跨进程共享 token/USD 配额 | P0 |
| Guardrails 四钩子三判决(pass/block/rewrite)纯函数 + 判决审计留痕 | P1 |
| Evolve 进化式程序搜索(EVOLVE-BLOCK+评估级联+islands+模型bandit+强制预算+零调用恢复) | P1 |
| Swarm 先持久化 dispatch 再执行 + 结果/控制事件原子提交 | P2 |

## 改进建议
1. [P0] claw_integration/agent_orchestrator 引入 Durable Execution 双机制：以 Lease(心跳续租决定驱动进程) + Revision(提交版本围栏拒陈旧写) 实现跨进程接管、僵尸执行器防护、cancel/drain 信号跨持有人投递
2. [P0] model_scheduler 增加持久化预算层：以 user/thread/org 维度记账 token + USD，准入先预留估算、调用后结算实际，超额在模型调用前拒绝，支持滚动窗口与告警
3. [P1] agent_orchestrator/tool_registry 引入 Guardrails 四钩子三判决模型：纯函数 onInput/onToolCall/onToolResult/onOutput 返回 pass/block/rewrite，非 pass 判决统一记录供审计
4. [P1] eval_observability/claw_integration 借鉴 Evolve 进化式程序搜索：用 EVOLVE-BLOCK 标记可变区 + 评估级联 + islands 分区 + 模型 bandit 分配算力 + 强制预算 + 零调用恢复，强化 Claw 自进化引擎
5. [P2] agent_orchestrator 采用 swarm 事务化调度：先持久化 task dispatch 再执行，结果与控制事件原子提交，无订阅者亦可推进
