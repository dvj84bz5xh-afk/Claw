### 核心发现

1. **一句话点破现存评测工具的通病**
   > "Every eval tool asks you to hand-author a dataset... That dataset is a guess about what might break. Production already handed you the real thing."
   手写数据集是"对可能出什么错的猜测"；而生产环境已经给了你**那次真正失败运行的完整轨迹**——输入、工具调用、模型响应全在。
   > **"The recorded run _is_ the test."**
   这句是整轮最值钱的一句。Claw 的 475 条改进项全是文字判断，没有一条绑着"那次失败的运行"。我们没有测试来源，只有意见来源。

2. **闭环五步，每步都有硬约束**
   `production trace → failure detection → regression test → CI gate → alert`
   - **Observe**：OTLP 接入，把 `agent.id`/`conversation.id`/`turn`/`step` 提升为一等索引列（否则 span 是一锅粥）；evaluator 是**trace 表上的列**而不是另一个标签页，判分结果 SSE 流式写回。
   - **Detect & triage**：在线判分每个 run（LLM-as-judge 在 conversation/run/span 三级 + 不需要模型的**结构化检查**）；失败按"结构签名 + 语义嵌入"**聚类**——31 次坏运行变成**1 个 issue 带计数**，并建议"哪个 evaluator 本可以抓到它"。
   - **Test**：一键把失败轨迹冻结成 **hermetic case**（输入/工具输出/模型输出打包成 fixtures），并附 **fail-to-pass 契约**——"该用例必须在旧代码上失败、在修复后通过，否则这次晋升不被信任"。
   - **Ship**：套件在 CI 里**离线重放 fabricated fixtures**，确定性、无 API key、**无模型花费**；`tracely gate` 非零退出 + commit status + PR 评论。
   - **Tell me**：告警是"何时 + 做什么"的流程图（闸门失败／出现没人见过的新失败模式／速率越线 → Slack／邮件／webhook／LLM 步骤）。

3. **fail-to-pass 契约是抗作弊的关键**
   普通回归测试最大的失效方式是"加了一个永远通过的用例"。要求"旧代码必失败、新代码必通过"把这堵住了：**没有红过的用例不算证据**。这一条直接对应我们"改进项写完就算完成"的松散验收。

4. **judge 需要先校准，才允许上闸门**
   有一个 calibration 屏：用人工标注对照 judge 判定，看每个 judge 的一致率、**漏报 vs 过报**，目的是"在你让它 gate 一个发布之前，先发现这是一个过度报警的 judge"。
   配套还有 **advisory verdict**：判分可以先只给建议、不参与拦截。
   我们有 LLM-as-Judge，但**没有任何校准记录**——等于让一个没量过准确率的裁判决定验收。

5. **多轮行为要用 scenario，不是单条用例**
   单条 trace 复现不了"被引导着一步步走偏"。它用两种 scenario：脚本化对话，或**红队模型自主追求的对抗目标**（goal achieved = FAIL）。后者把"越狱/被骗"变成可判定的失败条件。

6. **零成本重放的工程前提**
   重放不调模型、不调工具，全靠录制的 fixtures——所以 CI 里跑几百个 agent 回归用例是**$0 且确定性的**。这是"agent 回归测试"能落地的前提，否则每次 PR 都烧钱。

7. **摄入路径 blob-first**：原始数据**先落 S3 再进队列**。队列丢了证据不丢——与 11-04 agent-memory 的"先归档 trace 再蒸馏"同一条纪律。

### 改进建议

1. **[P0][eval_observability] 失败轨迹冻结 + fail-to-pass 契约**
   任务失败或被返工时，自动把该次 run 打包为用例：`{输入, 工具调用序列与返回, 模型输出, 期望判定}`，落到 `.workbuddy/regressions/<error_class>/<case_id>/`。晋升为"已修复"必须附 fail-to-pass 证据：用例在修复前的代码/配置上跑出失败、修复后跑出通过，两条记录都留档；**没有红过的用例不算修复证据**。

2. **[P0][eval_observability] judge 校准闸门**
   维护 `judge_calibration.json`：抽样人工标注 N 条判定，统计每个 judge 的漏报率与过报率。规则：未达阈值（如一致率 ≥ 0.85 且漏报率 ≤ 0.1）的 judge **只能是 advisory**，不得作为交付闸门；每次换模型或改 prompt 后校准失效，需重测。价值：现在等于让一个没量过准确率的裁判决定验收。

3. **[P1][eval_observability] 失败聚类，让台账自动长出来**
   对失败用例做两级聚类：结构签名（错误类型 + 首个失败工具 + 关键参数形态）+ 语义相似度；输出"同类 N 次"的聚合条目与"哪个检查本可抓到它"的建议。产出直接喂给 11-11 提议的 `error_classes.json`，避免靠人手归类。

4. **[P1][agent_orchestrator] 多轮 scenario 作为一等用例**
   单条 trace 复现不了"被一步步引导走偏"。增加 scenario 类型：脚本化多轮对话（预设每轮用户话术）与对抗目标（给定"让 agent 做出 X"的红队目标，达成即判失败）。价值：把"被骗/越界"从主观印象变成可判定失败。

5. **[P1][claw_integration] 回归套件进 CI 闸门**
   改动 harness（钩子/提示/工具签名/策略）的提交必须先跑回归套件：任一用例从通过转失败则非零退出、写 commit status、在 PR/提交里贴出失败用例与对应 error class。套件用录制 fixtures 离线跑，**不调模型**。

6. **[P2][storage] 摄入 blob-first**
   run 轨迹与工具输出先以原始 blob 落盘（按内容哈希命名），再进索引/队列；索引损坏或队列丢消息时可从 blob 全量重建。价值：与"索引可删可重建"配套，确保证据链不因管道故障断裂。

### 与 Claw 的关系判断
不引入依赖（Python 但为完整服务栈：Postgres + ClickHouse + Redis + MinIO，本地跑不动也无必要）。
它的价值是**把我连续八轮记录的那个断点接上了**：
- 11-11 说"错误必须入账"→ 这里给了入账的**载体**（冻结的失败轨迹）；
- 11-12 说"决策要可审"→ 这里给了验收的**抗作弊条件**（fail-to-pass）；
- 一直说的"缺 fitness 闭环"→ 这里给了闭环的**成本前提**（fixtures 离线重放 = $0），这才是以前跑不起来的真正原因。

最该抄的一句：**"The recorded run _is_ the test."** 我们一直在写"改进建议"，而正确做法是先把那次失败的运行录下来。
