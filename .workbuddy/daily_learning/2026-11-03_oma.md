- URL: https://github.com/open-multi-agent/open-multi-agent

- 一句话: 自托管 TS Agent 运行时，"组织能拥有、能审批、能离线审计"——无 telemetry、无托管控制面。

### 核心发现

1. **合规结论与执行结果分离**（governance floor）
   `runTeam(..., { governanceIntent:'required', requiredRoles:['reviewer','security'], requiredOrder:[...] })` 声明拓扑，跑完拿执行回执核对，产出 `governanceConclusion: satisfied | unsatisfied | not-applicable`。关键三点：
   - **成功 ≠ 合规**：README 明说 "A successful run can still leave governance requirements unmet"，应用必须单独检查结论；
   - **声明而非解析**：角色拓扑不从 goal 文本里猜，"The goal text is not inspected to choose this topology"，同一声明对中英文产出同一拓扑；
   - **非法声明在任何 agent 跑之前就抛错**（角色必须在名册里，order 必须是角色的排列）。

2. **审批对象是快照，恢复执行的就是被评审的那份内容**（durable approvals）
   四道闸门：`onPlanReady` / `onApproval`（轮次栅栏）/ `onTaskDispatch` / `onToolCall`。每道闸门显式列出"被评审内容"（工具闸门是 name + model-issued input + Zod 校验后 input + agent + task + tool-call ID + `consequential` 标记）。`suspend` 后返回持久化请求，进程重启从同一份评审内容继续，且**该边界不再二次调用闸门**。职责切得干净：checkpoint 拥有"挂起的续跑"，独立 approval 行拥有"不可变请求 + first-wins 决定"，telemetry 丢失不影响决定。

3. **Run journal 回答另外三份记录答不出的问题：模型为什么看到这个**
   append-only 记录"哪些消息进了会话、模型实际看到哪些 block、工具跑了什么返回什么、context strategy 替换成了什么、plan/task 状态怎么动、checkpoint 落哪"。`enforceLineage` 开启后，出现无法解释的"模型可见 block"直接抛错而不是记录。两个克制：journal **不是**恢复机制（checkpoint 才是，journal 只在恢复时补一段可回放尾巴）；默认关闭且关闭时零成本（不分配 recorder、每个埋点都 guard）。API 只收实例，故意不提供 `journal: true` 简写——"没人能读回的日志没用"。

4. **协调者只规划一次，运行中不再介入**
   `runTeam()` = 一次模型调用把 goal 拆成带 assignee/dependency 的任务图 → 确定性调度器执行 → 第二次调用按已完成任务写最终答案。coordinator "is never consulted mid-run"，于是"完成的 run 就是可读回的数据"。配合：plan replay 冻结已批准的计划，consensus 用独立 judge 验输出。

5. **出口策略在连接前检查，且诚实标注覆盖不到的地方**
   `offline` / `allowlist` 在内置 adapter 建连之前判定；**子策略只能收紧父策略**；"an unenforceable transport fails closed"；同时明确写出 process 与 ACP 后端不在此策略范围内。verifyRun 也只声称"检查记录来源与内容的一致性"，并主动否认"不能证明日志没被编辑"。

### 可借鉴点

| 优点 | 优先级 |
|------|--------|
| 声明式治理角色 + 事后核对回执，产出独立于"任务成功"的 compliance 结论 | P0 |
| 审批绑定快照：评审哪份就跑哪份，恢复时不再问第二次 | P0 |
| 模型可见边界可解释（lineage），无法解释即失败而非静默 | P1 |
| 协调者单次规划 + 确定性调度，完成后 run 可读回 | P1 |
| 出口策略子级只能收紧 + 不可执行即 fail-closed + 标注盲区 | P1 |
| 审计工具主动声明自身证明力的上限（一致性 ≠ 未被篡改） | P2 |

### 改进建议

1. **[P0][eval_observability] 交付闸门拆成两个结论：`deliveryStatus` 与 `governanceConclusion`**
   现状 Guardrails 四钩三判把"任务完成"和"过程合规"混在一个 pass 里，交付验收闸门过了就等于合规。改为：声明 requiredSteps/requiredOrder（如 plan→review→verify），执行后核对 run 记录，输出 `satisfied/unsatisfied/not-applicable`；`unsatisfied` 不篡改 run 成功状态，但阻断"可发布"标记。声明非法（引用不存在的步骤）在开跑前抛错。价值：让 445 条改进项的"是否真的被验证过"有独立字段可查，直击短板①。

2. **[P0][claw_integration] 审批记录不可变 + 恢复走同一份快照**
   现状 checkpoint 能续跑，但"批准了什么"没有独立载体，重启后靠重新推断。改为 approval 独立存一行（request 不可变、decision first-wins、绑定 plan/task/toolCall 内容哈希），恢复时按该行的快照继续且不再二次征询。价值：补齐"人批的"与"机器跑的"之间的可核对链条，支撑短板③。

3. **[P1][context_injector] 模型可见 block 的 lineage 校验**
   注入器现在记录"注入了什么"，但不校验"模型最终看到的每个 block 溯源到哪"。加 `enforceLineage` 开关：无法解释来源的 block 抛错。价值：上下文污染与注入失效可定位，而不是靠输出猜。

4. **[P1][agent_orchestrator] 规划与执行分离：coordinator 只在开头跑一次**
   现状编排过程中允许 re-plan，漂移无痕。改为首轮产出任务图后锁定（plan id + 内容哈希），运行中不回调规划器，事后可 `runFromPlan()` 复现。价值：run 可回放、可对比，评测有稳定基线（呼应短板①）。

5. **[P1][tool_registry] 出口策略收紧语义**
   工具侧 allowlist 加"子作用域只能收紧父作用域"，并对无法执行的传输直接 fail-closed；同时在文档里标注哪些后端不受此策略约束。价值：避免"配了策略但实际没生效"的假安全感（呼应短板④）。

6. **[P2][eval_observability] 审计结论分级**
   报告里区分"记录一致性可验证"与"未被篡改"两档，工具不得越级声称。价值：审计由工具自证是短板④的核心，先把话说明白比加密更便宜。

### 判断
OMA 与我们已学的 sandbase-harness（runtime 契约）、nono（能力代理）、agent-skills-platform（五件套）互补：那三个解决"能不能跑 / 能不能碰 / 算不算技能"，OMA 解决**"跑完了能不能证明它按规矩跑的"**。它最值得抄的不是代码而是三处"分离"：成功与合规分离、审批与续跑分离（快照绑定）、日志与恢复分离（journal 只审计不兜底）。Claw 当前把这三对都揉在一起，是最省力的改造点。
