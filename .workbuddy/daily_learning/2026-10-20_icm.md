### 学习项目: RinDig/Interpretable-Context-Methodology (ICM)
- URL: https://github.com/RinDig/Interpretable-Context-Methodology
- Stars: 1,359 | 语言: Python | 最近更新: 2026-10-06 | 论文: arXiv 2603.16021
- 一句话: **用文件夹结构当 Agent 架构** — 编号目录=执行序，Markdown=提示词与上下文，单 Agent 读对文件就完成原本需要多 Agent 框架的流水线

### 项目概述
反对"用框架代码表达编排"：CrewAI/LangChain/AutoGen 能跑，但改步骤顺序、换 prompt、加阶段都要改代码+重新部署。ICM 的观察是——如果每阶段的提示词与上下文本身就是组织好的文件，就不需要多 Agent 和协调框架，只需要**一个 Agent 在正确时刻读正确的文件**。Unix 管道的现代翻版：一个阶段一个职责、纯文本作通用接口、上一阶段输出即下一阶段输入。

### 核心发现
1. **五层上下文加载（读够即停）**：L0 `CLAUDE.md` 身份常驻(~800 tok) → L1 `CONTEXT.md` 任务路由(~300 tok) → L2 `stages/NN/CONTEXT.md` 阶段契约(~200-500 tok) → L3 references（品牌/语气/构建规范/领域知识，一次配置跨 run 复用="工厂"） → L4 output（本次 run 的工作产物）。单阶段实际上下文 **2,000-8,000 tok**，对比单体式全量注入 30,000-50,000 tok。
2. **L3 与 L4 的本质区分**：L3 是"要内化为约束与模式"（照这样写/用这些颜色/守这些约定），L4 是"要作为输入被加工"（把这份研究变成脚本）。两者对模型的要求不同，混在一起会互相干扰。
3. **Stage Contract 三段式**：每个 `stages/NN/CONTEXT.md` 固定写 Inputs 表（来源 / 文件位置 / **读哪一节** / 为什么读）、Process 步骤、Outputs 表（产物 / 落盘路径 / 格式）。Inputs 表是"控制点"——把"读什么"从猜测变成**显式、可编辑、可审计**的清单。
4. **文件系统承担编排职责**：阶段顺序=文件夹编号；上下文裁剪=目录层级；状态管理=磁盘文件；阶段间协调=一个目录的 output 就是另一个目录的 input。`_config/`+`shared/`+`skills/` 放 L3 稳定知识。
5. **每个产物都是人工编辑面**：人在 `01-research/output/` 改完文件，跑到阶段 02 时 Agent 直接读走人的版本 —— 天然 HITL，无需审批 UI 或状态机。
6. **默认玻璃盒可观测**：状态即文件系统，"没有日志层要建、没有仪表盘要配"，打开文件夹就能看全链路；每阶段产物可 commit，得到整条流水线的行为版本史，diff/回滚用标准 git。
7. **可移植性即交付物**：workspace 就是一个文件夹，可 zip/邮件/云同步/git 转交客户；客户自己改 prompt 改阶段，不需要开发者参与部署。setup questionnaire 一次性配置"工厂"，之后每次 run 只换输入。
8. **边界很清楚**：实时紧耦合多 Agent 协作、高并发多租户、自动化复杂分支 → ICM 不适用（需消息总线/队列/脚本化），此时框架仍是正解。

### 可借鉴点
| 优点 | 优先级 | 说明 |
|------|--------|------|
| 五层上下文分层 + "读够即停" + Inputs 表显式作用域 | P0 | Claw 已有"技能维度"三级 token 控制，缺"**阶段维度**"的分层契约 |
| Stage Contract（Inputs 表/Process/Outputs 表）作为线性流水线原语 | P0 | 给 Claw 一个零框架、可 diff 的轻编排模式，与 swarm 并存 |
| output/ 作为人工编辑面（人改完下一阶段直接读） | P1 | 比审批弹窗更低摩擦的 HITL |
| 状态即文件系统 → 玻璃盒可观测 + git 版本史 | P1 | 免建日志层/仪表盘，run 可完整回放与审计 |
| workspace 目录即交付物（可移植/可交接/客户自改 prompt） | P2 | 对应 Claw 的 Skill/Workspace 打包分发与外部交付 |

### 改进建议
1. **[P0][context_injector] 五层上下文分层加载**：把注入切成 L0 身份(L0 常驻 ≤800 tok)/L1 任务路由/L2 阶段契约/L3 稳定约束(项目 profile+品牌+规范)/L4 本次产物；每个 run 带 Inputs 表声明"读哪些文件、读哪一节、为什么"，按层读够即停，目标把单步注入压到 2-8K tok。价值: 直接降低长任务上下文开销与漂移，且注入变成可审计清单。
2. **[P0][agent_orchestrator] Stage Contract 线性流水线原语**：新增 `stages/NN/CONTEXT.md` 规范（Inputs 表/Process/Outputs 表+可选 checkpoint/audit），编号目录即 DAG 的线性特例；复杂分支/高并发仍路由到现有编排器。价值: 覆盖"顺序+人工复核+可重复"这类占多数的工作流（报告、课件、weekly digest），开发成本近乎为零。
3. **[P1][claw_integration] 人工编辑面交接**：每阶段产物强制落盘为可读 Markdown（带 metadata header），下一阶段默认读取磁盘现状而非内存快照；编辑即介入，无需新增审批 API。价值: HITL 从"打断式确认"变为"就地改文件"，同时天然获得审计轨迹。
4. **[P1][eval_observability] 状态即文件系统的玻璃盒 run**：`runs/<run_id>/stages/NN/{input,output}/` 全量落盘，提供 `claw replay <run_id>` 按阶段回放与 diff；不新建日志系统，直接用 git 存历史。价值: 事故定位从"翻日志"降为"打开文件夹"，并为 point-in-time 评测提供天然快照。
5. **[P2][skill_system] Workspace 可移植打包**：把 skill+配置+阶段目录打成单一可移植 bundle（zip/git），支持外部交付与客户自改 prompt，并记录 bundle 版本。价值: 让 Claw 产物可作为"可交付的 AI 工作流"对外分发，而非只在本地运行。

### 对 Claw 的定位判断
ICM 与 Claw 的 `Markdown-as-Truth` 同源，但把这条原则推进到**编排层**：Claw 目前是"框架编排 + 记忆/技能文件化"，ICM 是"连编排本身都文件化"。二者不冲突——Claw 应以框架编排处理动态多 Agent 场景，同时补上"零依赖线性流水线"轻模式；最大短板不在表达力而在**上下文注入的粒度**（技能维度已做，阶段维度空缺）与**run 级可回放**。
